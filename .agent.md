# FUJU Backend - Agent Instructions

This file provides guidelines for AI agents (GitHub Copilot, etc.) working on the FUJU Backend project.

## Project Overview

- **Type**: SNS (Social Network Service) Backend
- **Language**: Go
- **Architecture**: Clean Architecture
- **Authentication**: Bearer JWT access token issued by AuthCore (see pkg/authcore). Backend validates via RFC 7662 introspection.
- **Database**: PostgreSQL
- **Cache**: in-memory (AuthCore introspection TTL=30s). No Redis dependency.
- **API**: REST/HTTP

---

## Core Principles

### 1. Clean Architecture Adherence

**MANDATORY**: All code changes must respect the Clean Architecture layers:

```
Domain → Usecase → Repository → Handler → Middleware
```

- **Domain Layer**: Pure business logic, no external dependencies
- **Usecase Layer**: Business logic orchestration
- **Repository Layer**: Data persistence abstraction
- **Handler Layer**: HTTP request/response handling
- **Middleware Layer**: Cross-cutting concerns

**Rules**:
- ✅ Domain knows nothing about external systems
- ✅ Repository depends on Domain interfaces, not vice versa
- ✅ Handlers depend on Usecases, not databases
- ❌ NO circular dependencies
- ❌ NO direct database calls in handlers
- ❌ NO external API calls in domain entities

### 2. Go Standard Library Preference

**Philosophy**: Use Go standard library wherever possible.

**Allowed**:
- `net/http` for HTTP server
- `encoding/json` for JSON marshaling
- `database/sql` for database access
- `crypto/*` for cryptographic operations
- `time`, `fmt`, `log`, `context`, etc.

**Avoid**:
- Third-party HTTP frameworks (Gin, Echo)
- Third-party ORM libraries (gorm, sqlc)
- Third-party logging frameworks (logrus, zap) - use structured JSON instead

**Exception**: Only import third-party packages if they solve a critical problem not addressable with stdlib:
- PostgreSQL driver: `github.com/lib/pq` (necessary for database access)

### 3. Error Handling Strategy

**MANDATORY Pattern**:

```go
// Domain error
type AppError struct {
    Code       string // e.g., "USER_NOT_FOUND"
    Message    string
    StatusCode int
    Err        error // underlying error
}

// In handlers, convert domain errors to HTTP responses
func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request) {
    user, err := h.usecase.GetUser(ctx, id)
    if err != nil {
        // Wrap and return appropriate HTTP status
        handleError(w, err)
        return
    }
    // ... response
}
```

**Rules**:
- ✅ Wrap errors with context: `fmt.Errorf("failed to get user: %w", err)`
- ✅ Use custom error types for domain errors
- ✅ Log errors with sufficient context (user ID, request ID, etc.)
- ✅ Return consistent error responses (use swagger.yaml schema)
- ❌ NO panic() in production code
- ❌ NO silent error swallowing
- ❌ NO logging sensitive data (passwords, tokens)

### 4. Testing Requirements

**MANDATORY**:
- Minimum 80% code coverage
- All business logic must have unit tests
- All usecases must have tests (with mock repositories)
- All handlers must have integration tests

**Test File Naming**:
- Production: `user.go` → Test: `user_test.go`
- Use `*_test.go` suffix for all test files

**Testing Guidelines**:

```go
// Use table-driven tests for multiple scenarios
func TestGetUser(t *testing.T) {
    tests := []struct {
        name    string
        userID  int64
        wantErr bool
    }{
        {"valid user", 1, false},
        {"invalid user", 0, true},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            // test code
        })
    }
}
```

- ✅ Use `testing.T` from standard library
- ✅ Mock repositories for usecase tests
- ✅ Use real PostgreSQL for integration tests (in CI)
- ✅ Write descriptive error messages in assertions
- ❌ NO `t.Fatal()` in test cleanup
- ❌ NO flaky tests (use deterministic test data)

### 5. Naming Conventions

**Interfaces**:
```go
type UserRepository interface { }    // ✅ Good
type IUserRepository interface { }   // ❌ Avoid 'I' prefix
type UserRepositoryInterface { }    // ❌ Avoid 'Interface' suffix
```

**Functions**:
```go
func (u *User) Validate() error { }     // ✅ Good
func ValidateUser(u *User) error { }    // ✅ Good
func (u *User) GetID() int64 { }        // ✅ Good
func (u *User) ID() int64 { }           // ✅ Better (no Get prefix for accessors)
```

**Constants**:
```go
const MaxRetries = 3          // ✅ Good
const max_retries = 3         // ❌ Avoid snake_case
const DEFAULT_TIMEOUT = 30    // ❌ Avoid ALL_CAPS for non-const values
```

**Packages**:
```go
internal/domain/              // ✅ Good
internal/repository/          // ✅ Good
internal/handler/             // ✅ Good
pkg/logger/                   // ✅ Good
```

### 6. Authentication & Security

All clients (web and mobile) pass the AuthCore-issued access token as
`Authorization: Bearer <token>`. The backend introspects it per request
(cached 30s in-process via `pkg/authcore/cache.go`). Session lifetime,
refresh, and login flow are owned by AuthCore; this backend never sets
a `Set-Cookie` header of its own.

**Rules**:
- ✅ Always use HTTPS in production
- ✅ Trust AuthCore's introspection response for identity (`sub`, expiry)
- ✅ Attach `sub` to request context via `AuthMiddleware`
- ✅ Upstream 5xx from AuthCore → 503; `active=false` → 401
- ❌ NO JWT secret handling in this codebase (AuthCore owns signing)
- ❌ NO storing passwords (AuthCore owns credentials)
- ❌ NO logging tokens or sensitive data

### 7. Database & Transactions

**PostgreSQL Best Practices**:
- Use transactions for multi-step operations
- Connection pooling with optimized max connections
- Prepared statements to prevent SQL injection
- Indexes on frequently queried columns

**Soft Deletes**:
- Use `deleted_at` column for soft deletes
- Always filter: `WHERE deleted_at IS NULL`

**Transaction Management**:
```go
func (r *UserRepository) CreateUserWithProfile(ctx context.Context, user *User, profile *Profile) error {
    tx, err := r.db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("begin tx: %w", err)
    }

    // operations...

    if err := tx.Commit(); err != nil {
        tx.Rollback()
        return fmt.Errorf("commit: %w", err)
    }
    return nil
}
```

### 8. Caching Strategy

The only cache in the process today is the AuthCore introspection cache
in `pkg/authcore/cache.go` (in-memory, TTL=30s, keyed on the bearer
token). There is no Redis, no session store, and no application-level
cache layer.

**Rules**:
- ✅ Keep cache TTLs short enough to absorb short upstream blips only
- ✅ Handle cache misses gracefully (fall back to a live AuthCore call)
- ❌ NO storing sensitive data in cache beyond the introspection result
- ❌ NO reintroducing a distributed cache without a concrete consumer

### 9. Logging

**Structured JSON Logging**:

```go
logger.Info("user_created", "user_id", userID, "email", email, "request_id", requestID)
// Output: {"timestamp":"2026-04-14T10:30:00Z","level":"INFO","user_id":1,"email":"user@example.com","request_id":"req123"}
```

**Context-aware Logging**:
- Include: timestamp, level, request_id, user_id, method, path, status code, duration
- Never log: passwords, tokens, sensitive personal data

**Logging Levels**:
- DEBUG: Detailed debugging information
- INFO: General informational messages
- WARN: Warning messages for unexpected conditions
- ERROR: Error messages for failures

### 10. API Response Format

**Consistent Response Structure**:

```go
// Success
{
    "data": { /* resource */ },
    "meta": {
        "timestamp": "2026-04-14T10:30:00Z",
        "request_id": "req123"
    }
}

// Error
{
    "code": "INVALID_REQUEST",
    "message": "Email is required",
    "timestamp": "2026-04-14T10:30:00Z"
}
```

### 11. Context Usage

**MANDATORY**: Always pass `context.Context` as the first parameter:

```go
func (r *UserRepository) GetUser(ctx context.Context, id int64) (*User, error)
func (u *UserUsecase) CreateUser(ctx context.Context, user *User) error
func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request)  // Note: use r.Context()
```

**Examples**:
```
feat(posts): Add reply listing handler

return the immediate children of a given post, ordered oldest-first,
paginated by offset/limit, and hydrated with author / like state via
the shared post hydrate helper.

Closes #123

feat(user): Create user profile endpoint

test(post): Add table-driven tests for post validation

fix(middleware): return 503 when AuthCore introspect times out

docs: Update API documentation in swagger.yaml
```

## Common Anti-Patterns to Avoid

### ❌ Anti-Pattern 1: Mixing Layers
```go
// BAD: Handler directly queries database
func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request) {
    rows, _ := h.db.Query("SELECT * FROM users WHERE id = $1", id)
    // ...
}

// GOOD: Handler uses usecase
func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request) {
    user, _ := h.usecase.GetUser(r.Context(), id)
    // ...
}
```

### ❌ Anti-Pattern 2: Silent Error Handling
```go
// BAD
_, _ = h.userRepo.GetUser(ctx, id)  // No error handling

// GOOD
user, err := h.userRepo.GetUser(ctx, id)
if err != nil {
    return fmt.Errorf("get user: %w", err)
}
```

### ❌ Anti-Pattern 3: No Testing
```go
// BAD: No tests for business logic

// GOOD: Table-driven tests
func TestCreateUser(t *testing.T) {
    // test cases...
}
```

### ❌ Anti-Pattern 4: Hardcoded Values
```go
// BAD
const dbURL = "postgres://localhost:5432/fuju"

// GOOD
dbURL := os.Getenv("DATABASE_URL")
if dbURL == "" {
    return errors.New("DATABASE_URL not set")
}
```

### ❌ Anti-Pattern 5: Logging Sensitive Data
```go
// BAD
logger.Info("user created", "password", password)

// GOOD
logger.Info("user created", "user_id", user.ID)
```

## Code Review Checklist

When reviewing code or receiving feedback, ensure:

- [ ] Code follows Clean Architecture layers
- [ ] No circular dependencies between packages
- [ ] Standard library used; minimal third-party packages
- [ ] Error handling is comprehensive
- [ ] Tests added and coverage >= 80%
- [ ] No hardcoded values or secrets
- [ ] No sensitive data in logs
- [ ] Function signatures include context
- [ ] Database operations use transactions where needed
- [ ] API responses follow consistent format
- [ ] Swagger/OpenAPI updated if needed
- [ ] Commit messages follow convention

## When Implementing New Features

Follow this process:

1. **Plan**:
   - Identify which layers are affected
   - Sketch domain entities and interfaces
   - Consider error scenarios

2. **Implement Domain**:
   - Define entities and business rules
   - Write domain tests

3. **Implement Repository**:
   - Define repository interface in domain
   - Implement with PostgreSQL
   - Write integration tests

4. **Implement Usecase**:
   - Orchestrate repository logic
   - Handle domain errors
   - Write usecase tests with mocks

5. **Implement Handler**:
   - Define HTTP endpoint
   - Validate input
   - Convert errors to HTTP responses
   - Update swagger.yaml

6. **Test E2E**:
   - Manual testing
   - Verify CI/CD pipeline passes
   - Request code review

## Questions & Escalation

For ambiguous situations, default to:
1. **Safety**: Choose the more conservative approach
2. **Readability**: Code should be understandable without comments
3. **Testability**: Design code to be testable
4. **Performance**: Optimize after profiling, not prematurely
5. **Consistency**: Follow existing patterns in the codebase

If uncertain, ask in a comment or PR review rather than guessing.
